# An open review of Malinois 1.12 (87) at `4ae94ef`

**Reviewer:** DeepSeek V4.1 Flash (1017). **Date:** 2026-11-11.

**Tests I ran:** none. The full suite's result is the owner's (2,269 on iOS 27.0, 2,269 on iOS 18.0, and the macOS lane, as the prompt states); I did not repeat it, and I did not boot a simulator. I checked the claims below by reading the shipped code, the tests, and the documents. The probes I would run are named under each finding.

**What I did not read:** `_REVIEW_PROMPT.md` and every other reviewer's report or notes. I changed nothing but this file.

---

## 1. For the owner, in plain English

My overall judgement is that **the 1.12 set-aside feature itself is carefully built**: I could not find a way to use it to get past the PIN, to delete a photo the live log still names, or to make an unsigned set-aside ZIP pass the evidence verifier. The plain-file/no-link rules, the UUID-only file-name rule, the "other log / capture still being saved" checks, and the fail-closed notices are all present and are tested more thoroughly than most features in the app. The evidence verifier's core checks also looked sound: a changed record, a changed photo, a missing signature, a counter gap, an added statement, and a key not certified for Malinois are all reported rather than passed.

The problems that matter, most serious first:

1. **On an iPhone with no passcode, the "brute-force lockout" is much weaker than the app and the listing imply.** A forced restart clears the current wait (the count survives, but the wait does not). A thief with the phone can try one PIN, force-restart, try the next, and so on. A 4-digit PIN is then ten thousand restarts, not ten thousand waits. The app already warns that a phone with no passcode is open after a restart; it does **not** say that the PIN lockout can be skipped the same way, and `KeychainService`'s own comment assumes a device passcode. **What to do:** at minimum, say this in the arming-screen warning, `README.md` and `SECURITY.md`; better, refuse to arm without a device passcode, or require a 6-digit PIN and a lockout that cannot be skipped by a restart. This is a judgement: the threat model assumes a passcode, but the app allows the other configuration and advertises the lockout without the exception.

2. **The public README's invariant "There is no delete control for records; only the log's size limits remove them" will be false when 1.12's source is published.** The Event Log now has a Delete control for a set-aside log, and it removes that log's records (and the photos and clips only it names). There is no `readme-edits/1.12.json` in this folder, and the release tool can be given `none`, so the public README would keep the old sentence. The private 1.12 `README.md` is accurate; the public one is not. **What to do:** add the 1.12 README edit (or edit the mirror's README) before the public source is pushed. This is a text fix, not an app binary fix, but the public source is part of the release.

3. **A damaged journal line, or a journal that cannot be read at launch, is dropped without telling the owner.** The journal is the app's crash net. `EventStore.journaledEvents` deliberately skips a line it cannot decode, and `recoverFromJournal` returns silently when the file cannot be read. Home has a notice for a journal that cannot be **written**; it has none for one that cannot be **read** or for skipped lines. The event may still be in the main log; if it is not (the kill window the journal exists for), it is gone with no notice. This is an old limit, not new in 1.12, but it is the kind of silent evidence loss this review is for.

4. **The Apple Watch can silently drop a queued alert at the 1.12 ten-second deadline.** `WatchLinkWakes` gives a background wake back after 10 seconds even if relayed alerts are still in flight; the code says plainly that an alert not yet posted is lost. The watch app's screen can still say alerts will arrive, and nothing on the watch says one was missed. The iPhone's Event Log still has the event, but the wrist alert the owner relies on may not. This is a deliberate trade against watchOS killing the app, but the cost is not in the owner-facing words.

5. **Sharing a set-aside log sends the whole file, including records the screen could not read and other events, with no warning at the Share button.** The screen's explanation is about the records it could read; the Share button has no caption saying the ZIP is the whole log as kept. The ZIP's own README says it, but the owner sees the share sheet first. This is a privacy/consent issue, not a code defect: the design deliberately sends the file as kept.

6. **After a Delete that leaves photos or clips behind, the Event Log's notice is kept in memory only.** If the app is killed or relaunched before the owner dismisses it, the notice is gone. The ADR says the notice stays "until the owner dismisses it"; the code's comment says "Kept in memory only." The owner may believe the confirmation's promise that the photos and clips were deleted.

7. **A wrong PIN may not show the red "Incorrect PIN" line.** The pad sets `error = true` and then clears the digits; the `onChange(of: digits)` clears `error` again. The shake and haptic remain; the words may not. This is cosmetic, and I mark it SUSPECTED because I did not lay out the screen to watch it.

**Would I let 1.12 (87) go to TestFlight and then the App Store?** **Yes to TestFlight now.** **For the App Store, yes after the two High items are fixed in the words** (the public README and the no-passcode warning/docs). The public README and the docs are text; the arming-screen warning is a small text change in the app, so if that is included, rebuild and re-run the gate's smoke checks. I would fix the watch wording and the set-aside Share caption before the public source is published; the delete-notice persistence and the PIN error line can be 1.12.1 if the owner accepts them. I found no Critical code bypass, no way to forge a bundle, and no evidence of media loss in the ordinary set-aside Delete path.

## 2. Findings

### DVF-1 — On an iPhone with no passcode, a restart skips the PIN wait, so a 4-digit PIN can be guessed a restart at a time

- **Severity:** High.
- **Status:** VERIFIED for the code and the existing test; SUSPECTED for the practical time to guess, which depends on restart time.
- **What is wrong:** The PIN lockout deadline is stored as `deadlineUptime|setUptime`. `KeychainService.lockoutRemaining` deliberately reads a stored deadline whose `setUptime` is above the current uptime as stale and returns 0 — that is the reboot path. The failure count survives, but the current wait does not. `KeychainService`'s comment says a reboot "buys an attacker nothing" because iOS requires the device passcode before first unlock. That is true on a phone with a passcode. On a phone with no passcode, the phone boots open, the app can be opened, and the attacker can try again at once. The app's arming screen warns that a forced restart opens such a phone and ends Guided Access; it does not say the PIN wait is also cleared. `README.md:557-559` and `SECURITY.md:648` say the phone is open, "though the Malinois log still needs the PIN"; a reader can take that as "the PIN still protects it."
- **Concrete situation:** The owner removes the iPhone passcode (or never sets one) and arms with the default 4-digit PIN. A thief force-restarts the phone (Guided Access ends), unlocks it, opens Malinois, and tries `0000`. Wrong. Force-restart, unlock, try `0001`. Each cycle costs one wrong guess; the stored failure count rises, but the 30s/1h wait is skipped each boot. Ten thousand restarts is days, not the years the on-screen lockout suggests. The attacker eventually reaches the Event Log and its photos. The wrong attempts on the Event Log gate are not recorded as events (only the armed pad's wrong PINs are), so the owner may see no trace of the guessing.
- **Evidence:** `Malinois/Services/KeychainService.swift:434-440` (the comment's assumption), `:558-565` (`lockoutRemaining` returns 0 after a reboot); `MalinoisTests/KeychainServiceTests.swift:60-73` (the test says "a reboot clears the current wait"); `Malinois/Views/PINViews.swift:707-708` (`BiometricKind.noPasscodeWarning`); `README.md:557-559`; `SECURITY.md:648`.
- **Smallest fix:** Write the exception down: in the no-passcode warning and in `README.md`/`SECURITY.md`, say "a restart also clears the current PIN wait; a 4-digit PIN can be tried one guess per restart — set a device passcode or use a 6-digit PIN." A code fix would be to refuse arming without a passcode, or to keep a wall-clock lockout that a restart cannot erase (knowing the clock can be changed on such a phone); that is a product decision, not a one-line fix.
- **Probe:** The existing `KeychainServiceTests` test already shows the wait clearing. A new pure test would plant `"1030|1000"`, call `lockoutRemaining(stored:uptime:wallNow:)` with `uptime: 5` (a restart) and assert 0, then show the stored failure count is still 5 and each further guess can run; it would settle the mechanical claim, not the timing.
- **Before 1.12 (87)?** The wording should be fixed before the App Store submission if the listing's "brute-force lockout" is to remain unqualified. The behavioural change (block arming / 6 digits) can be 1.12.1, with the owner's decision.

### DVF-2 — The public README's no-delete invariant becomes false with 1.12's set-aside Delete

- **Severity:** High (a published claim is false; documentation only).
- **Status:** VERIFIED.
- **What is wrong:** `_PUBLIC_README.md:146` says: "There is no delete control for records; only the log's size limits remove them, and SECURITY.md says which removals the log reports." In 1.12 the Event Log lists each set-aside log at its top, its screen has a `Delete` button, and `EventStore.deleteSetAsideLog` removes the log and at once the photos and clips only it names. Those are records. The internal `README.md:31` is correctly narrower ("no user-facing action to delete individual events"), but the public invariant is not. The folder has `tools/release/readme-edits/` only through `1.11.json`; `stage-public.zsh` accepts `--readme-edits none`, so the old sentence can be published unchanged.
- **Concrete situation:** A reader checks the public invariant against the 1.12 source and finds a Delete control; the README's "each invariant is checkable against the code and its tests" promise is broken. The owner's own release step counts this as the public statement of the app's data-retention rules.
- **Evidence:** `_PUBLIC_README.md:146`; `Malinois/Views/SetAsideLogView.swift:85-98` (the Delete button and confirmation); `Malinois/Services/EventStore.swift:2921-2937` and `:2967-3018` (the deletion and its media rule); `tools/release/README.md:230-234` (the per-release README edit file) and `tools/release/stage-public.zsh:53` (`none` is allowed); `ls tools/release/readme-edits` has no `1.12.json`.
- **Smallest fix:** Add `tools/release/readme-edits/1.12.json` with a `find` of the line and a `replace` such as: "There is no delete control for an individual record in the Event Log, and only its size limits remove records from it. A set-aside log is different: the owner can read, share or delete it as a whole, behind the Malinois PIN, and deleting it removes the photos and clips only it names; the launch's sweep then clears what no record names." Update the code/test citations beside it to `EventStore.deleteSetAsideLog` and the set-aside tests. Or edit the mirror README directly at the stage.
- **Probe:** `grep -n "no delete control for records" _PUBLIC_README.md`; `grep -n "Delete" Malinois/Views/SetAsideLogView.swift`; a `readme-edits` dry run of `stage-public.zsh` would refuse the tree if the count/text is wrong.
- **Before 1.12 (87)?** Before the public source is pushed. It is not an app-binary blocker, but it is a release blocker for the public source and a false published claim.

### DVF-3 — A journal line that cannot be read, or a journal file that cannot be read, is dropped without a Home notice

- **Severity:** Medium.
- **Status:** VERIFIED (the silent drop is stated in the app's own test).
- **What is wrong:** `EventStore.journaledEvents` decodes each newline-separated line with `try?` and silently skips a line it cannot decode. `recoverFromJournal` starts with `guard let data = try? Data(contentsOf: journalFile) else { return }`, so a journal that cannot be read at launch produces no flag and no notice; it simply returns. Home's `journalNotice` is driven by `journalDegraded`, which is set only by a failed **append/sync**. The event may also be in `events.json`; if it is not — the kill window the journal exists for — it is lost, and the owner is told nothing. A damaged line in the middle is dropped while later lines are kept, which the test states as today's behaviour.
- **Concrete situation:** The phone dies during a capture, after the journal line is written but before the full log write lands. On the next launch the journal's last line is torn; `journaledEvents` drops it; the event is not in `events.json`; the app starts with no record of it and no notice. The owner sees a shorter log and assumes nothing happened. The same happens if the journal file is unreadable for any reason (a bad restore, a permissions/bit-rot failure): the recovery returns with no sign.
- **Evidence:** `Malinois/Services/EventStore.swift:1701-1707` ("A garbage line ... is skipped"), `:1716-1718` (silent return on an unreadable journal), `:75` (`journalDegraded` is the write flag), `HomeView.journalNotice` (the only journal notice); `MalinoisTests/Item148DecoderFuzzTests.swift:120-132` ("an unreadable line in the middle is dropped as silently as a torn last line").
- **Smallest fix:** Add a `journalReadDegraded` (or reuse `journalDegraded` with a different sentence) set when `Data(contentsOf:)` fails or when `journaledEvents` had to skip any line, and show a Home line such as "Some recent events may not have been recovered from the event journal." Keep the tolerant parse; just tell the owner. If the line count matters, return `(events, skipped)` from `journaledEvents` and count the skips.
- **Probe:** A launch test with a journal holding one valid line for an event absent from `events.json` plus one garbage line; assert the valid event appears and the garbage is skipped; assert Home says a line was skipped. A second test makes `events.journal` a folder (or unreadable) and asserts the Home notice; today both show no notice.
- **Before 1.12 (87)?** Later (1.12.1). It is a real silent-loss path, but it is old, and the docs already say an abrupt power loss can lose evidence.

### DVF-4 — The Watch's ten-second wake deadline can silently lose a queued alert

- **Severity:** Medium.
- **Status:** VERIFIED for the mechanism; SUSPECTED for how often a real watch hits it.
- **What is wrong:** `WatchLinkWakes` gives every link wake back after `deadline` (10 seconds) if it is still held, and `WatchAppDelegate` releases a wake at that deadline even when `alertsInFlight` or `hasContentPending` says alerts remain. The code's own comment says "an alert not yet posted is lost either way." The watch app's status screen can still say alerts will arrive; nothing records a missed alert on the watch. The 1.12 What's New says the wake is handed back within 10 seconds, and the README says the watch shows the alerts; the cost is not in those words.
- **Concrete situation:** The iPhone records a tamper and relays several queued alerts. The watch wakes, the inbox reads its delivered-notification list (the 1.12 change gives the alerts of one run 2 seconds for those reads), and a slow list or a backlog uses the rest of the 10-second budget. The deadline gives the wake back; the watch is suspended before the remaining alerts are posted. The wrist never alerts for them; the iPhone's Event Log has them. The owner, relying on the watch, may not look at the phone.
- **Evidence:** `MalinoisWatch/WatchLinkWakes.swift:16-28` (the deadline and the lost-alert comment); `MalinoisWatch/WatchAppDelegate.swift:97-126` (wake handling and `finishLinkTasksIfDone`); `MalinoisWatch/WatchRelayInbox.swift` (the per-run list allowance); `store/APP_STORE_LISTING.md:259` (the 1.12 What's New wording).
- **Smallest fix:** At the deadline, post a local notification (when notifications are allowed) saying "A Malinois alert may have been missed — check the iPhone's Event Log", and record that the watch had in-flight alerts at the deadline. If a local notification is too much, put the caveat in the README and the watch's status screen. A stronger fix is for the iPhone to send a delayed summary that the owner can see if the watch missed the original.
- **Probe:** A watch-side test (the `Item212WatchWakeTests` harness) with a `delivered` closure that blocks and several `WatchAlertMessage`s; hold a wake, let the 10-second deadline fire with `alertsInFlight > 0`; assert the wake is given back and the remaining messages are not posted; assert the current code records no "missed" notice. The exact frequency can only be measured on a watch.
- **Before 1.12 (87)?** The wording and a small local notice can be 1.12; the deeper iPhone-summary fix can be later. At least do not publish "alerts arrive" without the caveat.

### DVF-5 — Sharing a set-aside log sends the whole file and records the owner did not see, with no warning at Share

- **Severity:** Medium (privacy/consent; deliberate design).
- **Status:** VERIFIED.
- **What is wrong:** `SetAsideLogShare.folder` writes the set-aside log **as kept**, byte for byte, and copies every media file in the real media folder whose name appears anywhere in those bytes. It does not restrict itself to the records the screen decoded, and it does not tell the owner that the ZIP contains all the other records in the file. The screen's explanation says "These are the records it could read"; the Share toolbar button has only the system "Share" accessibility label. The ZIP's README says it is the file as kept and not signed evidence, but the owner does not see that until after the share.
- **Concrete situation:** The owner has a set-aside log of 40 records; the screen reads 12. They tap Share to send it to building security. The ZIP includes all 40 (including the 28 parts the screen called unreadable), plus photos of other events. The owner believes they shared the 12 records they saw. The recipient gets more.
- **Evidence:** `Malinois/Views/SetAsideLogView.swift:115-125` (the Share button), `Malinois/Models/SetAsideLog.swift:357-378` (the file copied as kept and media found by byte search), `:278-280` (the screen's explanation), `:321-326` (the ZIP README); ADR 0078 decision 2 (the file as kept, deliberately).
- **Smallest fix:** Add a caption under the Share button, and a first line in the share sheet's text item: "This ZIP is the whole log as the phone kept it: it includes every record in the file, including parts this screen could not read, and the photos and clips it names. It is not signed." If the owner wants less, a second "Share only the readable records" would be a design change.
- **Probe:** A set-aside log with one readable record naming photo A, one undecodable record naming photo B, and both photos in Media; `SetAsideLogShare.folder` contains the log and both photos, while `SetAsideLog.reading` returns one record. The screen's `reading.records.count` and the ZIP's content then disagree; a test can assert the current behavior and the new caption's words.
- **Before 1.12 (87)?** A one-line UI/text fix is worth doing before the source is published; the share scope itself is the owner's design, so a later change is a judgement.

### DVF-6 — A Delete's "photos and clips may still be on this iPhone" notice is lost on relaunch

- **Severity:** Low (the owner sees it at the time; the loss is an edge).
- **Status:** VERIFIED.
- **What is wrong:** `EventStore.setAsideDeletionsToTell` is "Kept in memory only" (`EventStore.swift:68-72`). The Event Log's notice survives leaving the Event Log within the app session, but not a kill or a relaunch. ADR 0078 decision 6 says the notice stays "until the owner dismisses it there"; the code makes that true only until the process ends.
- **Concrete situation:** A Delete removes a set-aside log but leaves its photos because the event log on disk is a link or unreadable; the Event Log shows "Set-aside log deleted — Its photos and clips may still be on this iPhone..." The owner backgrounds the app; iOS kills it. On the next launch the Event Log has no notice; the photos remain; the owner believes the confirmation's "photos and clips ... are deleted" was fully carried out.
- **Evidence:** `Malinois/Services/EventStore.swift:66-72` and `:2940-2950`; `Malinois/Views/EventLogView.swift:93-104` and `:155-176`; ADR 0078 decision 6.
- **Smallest fix:** Persist the two pending outcomes (they are a two-case enum) in the store's folder or UserDefaults, protected like the log, and load them at launch; or derive a Home line from a marker until dismissed. The notices contain no evidence; a small JSON file is enough.
- **Probe:** Set `setAsideDeletionsToTell` to `[.deletedMediaLeft]`, rebuild the `EventStore` on the same root, and assert the notice is present; today it is empty.
- **Before 1.12 (87)?** Later (1.12.1). The ADR's wording should also be narrowed to "until dismissed or the app is relaunched" if the owner accepts the memory-only design.

### DVF-7 — A wrong PIN may not show "Incorrect PIN"

- **Severity:** Low.
- **Status:** SUSPECTED (not laid out on a screen).
- **What is wrong:** `PINEntryView.check()` sets `error = true` and then immediately sets `digits = ""`. The view's `.onChange(of: digits) { _, _ in error = false }` is meant to clear the error when the owner starts typing again, but it also fires for the programmatic clear. The red `Text("Incorrect PIN")` may therefore never render; the shake and haptic are the only feedback.
- **Concrete situation:** On Home's Event Log gate, the owner types a wrong 4-digit PIN. The pad shakes; the red "Incorrect PIN" line does not appear. The owner tries again; after five attempts the lockout message appears. The failure is still counted; the visual explanation is missing.
- **Evidence:** `Malinois/Views/PINViews.swift:534-536` (the text), `:567` (the `onChange`), `:640-645` (the `error = true; digits = ""` order). No test checks the text; `Item122` checks only the confirmation behavior after a wrong PIN.
- **Smallest fix:** Change the `onChange` to clear `error` only when a **new digit** is added (`new.count > old.count`), or set `error` after the `digits` clear in a separate state update, or use a distinct `showError` set on the submit.
- **Probe:** A laid-out `PINEntryView` with a real 4-digit PIN, wrong digits typed on the pad, then assert `"Incorrect PIN"` appears in the rendered text (add `.reportedOnScreen` in a scratch copy or use a window snapshot). If it does appear, close this as a non-finding.
- **Before 1.12 (87)?** Later; cosmetic.

## 3. Wrong claims in the documents

1. **`_PUBLIC_README.md:146` — "There is no delete control for records; only the log's size limits remove them."**
   **Why wrong:** 1.12's set-aside screen has a `Delete` control that removes the log's records and the photos and clips only it names (`SetAsideLogView.swift:85-98`, `EventStore.deleteSetAsideLog`). The public README is the source of the published claim; the internal `README.md:31` is accurate because it says "individual events". **Wording I would use:** as in DVF-2: "There is no delete control for an individual record in the Event Log, and only its size limits remove records from it. A set-aside log is different: the owner can read, share or delete it as a whole, behind the Malinois PIN, and deleting it removes the photos and clips only it names; the launch's sweep then clears what no record names."

2. **`store/APP_STORE_LISTING.md:256` (the 1.12 What's New) — "share it as your iPhone kept it ... with the photos and clips it names".** The ZIP contains only the named photos and clips **that are still on the iPhone**; a photo named by the log but no longer on disk is absent. The ZIP's README says exactly this (`SetAsideLogWords.readme`), and ADR 0078 decision 2 says "that were still on the iPhone when it was shared". The listing line was approved by the owner, so this is a judgement; **I would say** "with the photos and clips it names that are still on the phone".

3. **`store/APP_REVIEW_NOTES_FIELD.md:34` — "nothing is saved until a tripwire fires".** With the signal-loss response on (the default), a stationary armed phone that had a connection at arm time and loses it for about 30 seconds gets a **Signal loss** record and a best-effort frame **without a tripwire** (`MonitoringEngine+Jamming.swift:86-96`, `logBlackoutRecord`). The full `store/APP_REVIEW_NOTES.md:115-116` has the exception; the 4,000-byte field text does not. The field is not currently pasted (the notes say the owner leaves it as it was), so this is a **Medium** risk only if it is pasted. **Wording:** add "or, with the signal-loss response on (the default), when a stationary armed phone has been without its connection for about 30 seconds and the motion tripwire has not tripped in the last 10 seconds".

4. **`SECURITY.md:648` and `README.md:557-559` (the no-passcode passage) — the PIN is left as the remaining barrier without saying the lockout is per-boot.** The passage says a phone without a passcode is open after a forced restart, "though the Malinois log still needs the PIN". On that phone, a restart also clears the current PIN wait (`KeychainService.lockoutRemaining` and `KeychainServiceTests`), so the PIN can be guessed one restart at a time. The app's no-passcode warning (`PINViews.swift:707-708`) says only that the phone is open. **Wording:** "On an iPhone with no passcode, a restart also clears the current PIN wait: a 4-digit PIN can be tried one guess per restart. Set a device passcode, or use a 6-digit PIN and expect the log to be a weaker barrier."

5. **`README.md:161` — "Reaching **Disarmed** requires the **PIN**."** A countdown cancelled before it went live calls `disarm()` without a PIN (`MonitoringArmingFlow+Transitions.cancelArming`, `ArmingView.cancelArming`); the app records the cancellation and, on Pro, sends the disarm alert. The state does become `disarmed`. This is a precision issue, not a live-watch disarm; **I would say** "Reaching Disarmed from a live watch requires the PIN; a countdown cancelled before it went live needs none, and is recorded." The README elsewhere (`:471`) already explains the cancelled-countdown record, so the sentence should not be read as contradicted.

6. **`store/APP_REVIEW_NOTES.md:66-68` (1.11) and the field — no 1.12 line.** The 1.12 release adds a set-aside screen with a read-only record list, Share and a PIN-gated Delete. Apple's 2.3.1(a) asks for new features to be described with specificity; the owner's practice is to leave the field unless a line becomes untrue, and the 1.12 What's New covers it. This is **Low**, but a one-line 1.12 addition to the full notes (not necessarily the field) would keep the reviewer reference current.

## 4. Where I went

**Looked at and found sound:**

- **The set-aside log's file and media rules.** `SetAsideLog.all` lists plain `events.corrupt-…` files only; a folder or link is not listed. `SetAsideLog.read` reads a plain file only. `SetAsideLogShare.folder` takes the log as a plain file, copies only media under the store's exact 40-byte UUID.jpg/.mov name, only from a real media folder, and only plain files. `EventStore.deleteSetAsideLog` deletes a log only when its parent resolves to the store root and the entry is a plain file, and removes media only when it is named by the deleted log, not by the event log in memory or on disk, not by another set-aside log, and not by a capture's attachment intent. Where any of those cannot be read, it returns `.deletedMediaLeft` or `.notDeleted` and the Event Log says so. The tests in `Item122SetAsideLogTests` cover the link/folder cases, the escaped-name cases, the two-log cases, the unreadable-event-log case, the unreadable-capture case, and the partial-removal case. I did not find a path in that code that deletes media the live log names or that treats a folder/link as a file.
- **The PIN gates.** The Event Log, Settings and Test Sensors are reached only through Home's `pinGate`, which is opened after `KeychainService.verifyEntry` (or, for the two read surfaces, a bound biometric). Settings is PIN-only; disarm and PIN change are PIN-only; the set-aside Delete pad is explicitly constructed with `allowBiometrics: false`, so a face or finger cannot delete. `SetAsideLogDeleteSteps` enforces the PIN-first, one-entry-one-confirmation, background-closes rules, and the `Item122` tests lay out the real screen for wrong PIN, right PIN, cancel and background. The bind-to-enrolled-biometrics logic (`BiometricBinding`) compares `domainState.biometry.stateHash` and turns the unlock off on a change. I found no direct way to open the Event Log, Settings, or a Delete without the PIN or the owner's chosen biometric.
- **The evidence verifier's core.** `EvidenceVerifier.certify` checks Apple's App Attest chain to the built-in root at the certificate's judged time, the nonce over the authenticator data and the statement, the key ID/credential/COSE point, the app ID hash, a zero attestation counter, and the environment; `EvidenceBundle.check` verifies each signature over its statement hash, the export statement as the last signature, the counter gaps, the statements shown versus the export's named counters, the record's revisions, the attachment digests, and every other file in the bundle. A changed record, a changed photo, a missing signature, a missing statement, an added statement, or a key the bundle does not certify is reported as a problem or a named fact; the verifier's PASS text says what it cannot show. The ZIP layout/listing checks refuse links, `..`, duplicate names, `__MACOSX`, ZIP64, and a second archive. I did not find a cheap way to make a changed bundle pass.
- **The cloud's privacy boundary.** The app uses `privateCloudDatabase` only; the sensitive CloudKit fields are set through `record.encryptedValues`; the watch and the notification extensions read no event records; the alert texts are generic. The privacy manifest declares UserDefaults, SystemBootTime, and FileTimestamp with plausible Apple reasons, and the notification extensions have empty entitlements.
- **The siren and the response path.** The siren retries activation, reports an exhausted start on Home (`sirenNotice`), and asks for the speaker in Siren mode; a speaker refusal is checked and reported. The `escalate` path writes the signal-loss record before the warning/siren. I did not find a silent siren failure in the ordinary path; the no-passcode lockout and the watch deadline are the two "no sound" concerns I did find.

**Could not check, and why:**

- **No simulator or device run.** I did not create or boot a simulator, did not run the suite, and did not run a watch. The prompt says the full suite passed on this commit; repeating it would slow the other reviewers and would not change the code. The probe tests above are what I would run.
- **No real Guided Access, Face ID, Touch ID, App Attest, CloudKit, or watchOS.** The simulator cannot exercise these; I reasoned from the code and the tests' seams. In particular, the watch deadline behaviour and the actual frequency of a dropped alert can only be measured on a watch.
- **No long no-passcode brute-force timing.** The code and the existing test establish the wait is cleared by a restart; the time per guess depends on the device and the attacker's automation.
- **No App Review.** I read the listing, the reviewer notes and the privacy/support pages as a reviewer would, but I cannot predict Apple's decision; the 1.12 What's New and the set-aside Delete are the new review surface.
- **No proof of the public mirror's state.** `_PUBLIC_README.md` is the published 1.11 text in this folder; the 1.12 stage would regenerate the What's New and counts, but the invariant at line 146 is hand-written and would remain unless an edit is added. I checked the release tooling's requirement; I did not run `stage-public.zsh`.
- **The set-aside delete's transient race.** The `inMemory` snapshot is taken before the I/O queue; a journal-recovered event that appears in memory after that snapshot and before the deletion, and is not yet in `events.json`, could in principle name a file the set-aside log also names. I could not construct a reachable user sequence for it (the unlock reload normally precedes the Event Log; a fresh capture uses a new UUID), so I did not raise it as a finding. A probe would need to force the reload and the Delete into one window.

**One blind spot in how the app is tested:** the set-aside tests are extensive on the file/media rules, and the PIN tests are extensive on the armed pad, but there is no test that observes a **wrong PIN's visible "Incorrect PIN" line**, and no test that observes **Home after a journal read failure or a skipped journal line**. Those are the two places where the code's behaviour can differ from what the owner is told without a test noticing.
